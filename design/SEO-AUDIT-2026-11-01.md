# Audit SEO — The People's Room

Data: 1 novembre 2026. Baseline sorgente: `cea685f`. Superficie esaminata: dominio pubblico `https://thepeoplesroom.it/`, variante www, risposte HTTP, tutte le 11 pagine canoniche e relativo DOM Chromium con JavaScript, anteprima GitHub pubblica e artefatto Workers Static Assets.

## Esito

Il sito pubblico era già raggiungibile e tecnicamente indicizzabile: 11 pagine con HTTP 200, canonical HTTPS coerenti, sitemap di produzione con 11 URL, robots senza blocchi alle pagine, un H1 per pagina e un vero 404 sui percorsi inesistenti. Non sono emersi blocchi critici all'indicizzazione.

I problemi verificati erano description identiche su tutte le pagine, titoli di servizio poco informativi, anteprima GitHub indicizzabile, segnali Home misti e alias affidati a refresh/JavaScript. Le correzioni sono pubblicate sul dominio principale nella release `ce75f6d8-7d5b-44bd-bbe0-775920ffbec3` e verificate nell'artefatto locale e nel DOM pubblico. Il sorgente corrisponde al commit `b0af3af`.

Non sono disponibili Search Console, Google Business Profile, dati analitici o un baseline di ranking. Non si deducono traffico, posizioni, CTR o incremento delle prenotazioni da un controllo tecnico.

Il JSON-LD deriva indirizzo, CAP, città, provincia e orari da quella fonte. Il build si ferma se il formato o i giorni cambiano senza revisione dello schema.

## Crawl, heading, immagini e collegamenti

- Tutte le pagine canoniche erano accessibili con HTTPS e una singola H1 nel DOM; i loghi nelle H1 About/Vivi hanno testo alternativo. Gli H1 editoriali e i titoli brand delle Rooms restano fedeli al design.
- Nessuna immagine del DOM esaminato mancava dell'attributo `alt`. I visual decorativi hanno `alt=""`; non sono considerati un errore SEO.
- Le pagine di servizio sono raggiungibili da link HTML nella navigazione Home; nessuna delle 11 risulta orfana. La prenotazione è accessibile dalla Home e da TPR Move.
- Le due immagini Home con `currentSrc` vuoto sono placeholder delle facce animate, non risposte HTTP 404: non classificate come asset rotti.
- Esistono asset originali/lossless pesanti: Home eventi circa 3,14 MB, Home hero circa 2,32 MB; alcune foto eventi oltre 1 MB. La dimensione è un rischio prestazionale da misurare, non una prova di Core Web Vitals insufficienti. Nessuna ricompressione, sostituzione font o alterazione delle maschere è stata eseguita nell'audit SEO. La verifica di LCP/CLS da laboratorio è separata e non equivale a CrUX o Search Console.
- Il sito usa un'unica lingua italiana con `lang="it"`; non occorrono alternate hreflang senza vere varianti linguistiche.

## Verifica e limiti

Il robots.txt all’origine GitHub (`https://mircoaurelio.github.io/robots.txt`) restituisce 404; il file nel percorso `/tpr-site/` non governa il crawl dell’intera origine. L’esclusione effettiva delle pagine preview è affidata al meta noindex.

Le prove prima dell'intervento sono in `.qa/seo/live-responses-before.json`, `rendered-before.json`, `crawl-summary-before.json` e `github-preview-before.json` (diagnostica ignorata da Git). Il fetch live esegue solo GET/HEAD e l'audit browser blocca gli invii.

Regressioni osservate rosse prima del codice: titolo Home non descrittivo; WebSite assente; `/gallery/` HTTP 200 anziché 301; pagine preview senza noindex. Dopo le correzioni: test build completo 9/9 passati e suite Python completa 6/6 passata (incluso il generatore). I test del build parsano gli HTML reali con Chromium e interrogano il router locale Cloudflare per tutte le 54 varianti note, inclusa conservazione query e ancore. Sono mantenuti i controlli su asset, privacy, newsletter, limiti e file non pubblici.

Il router segue la [funzionalità ufficiale `_redirects` per Workers Static Assets](https://developers.cloudflare.com/workers/static-assets/redirects/). Non cambia `run_worker_first` o i backend newsletter/inquiry. La privacy resta Iubenda 70616678 e la prenotazione resta il widget Mindbody esistente. Il vecchio comando `scripts/seo_audit.py` ora esamina `dist-cloudflare/`, deriva le 11 pagine da `routes.json`, riconosce le copie raggiungibili tramite redirect nativo e segnala davvero description duplicate e asset con il prefisso GitHub errato. Non richiede JSON-LD su ogni pagina o metadati Twitter come condizioni di indicizzabilità.

Il crawl finale dell'artefatto locale (`.qa/seo/rendered-after-local.json`) conferma 11/11 risposte 200, 11 description uniche, `index,follow` su tutte le pagine, una H1 ciascuna, nessun `alt` mancante e zero errori JavaScript. I 29 target interni distinti controllati restituiscono 200. Il JSON-LD compare nel DOM sulla Home (`WebSite`) e in Contatti (`LocalBusiness`). Le richieste verso servizi esterni e tutti gli invii sono stati bloccati durante questo controllo.

## Prossime verifiche dopo pubblicazione

1. Controllare sul dominio pubblico le 11 pagine, i 301 e il sitemap; confermare `index,follow` in produzione e `noindex,follow` su GitHub.
2. Eseguire Rich Results Test/Schema.org Validator sul JSON-LD pubblicato e, se disponibile, URL Inspection/Search Console sul sitemap canonico.
3. Usare dati reali di Search Console per decidere eventuali affinamenti dei titoli o contenuti: separare query brand, servizi e prenotazioni, senza attribuire a priori aumenti di traffico.
4. Verificare con il titolare Google Business Profile, indirizzo, orari, categoria e link prenotazione. Profilo, recensioni e directory non sono stati modificati né valutati senza accesso.
5. Considerare il redirect www solo come rifinitura edge e misurare le prestazioni preservando gli asset e la qualità richiesta dal design.
